## 一、发热根源（已读源码，结论确定）

应用运行后手机发烫，是 **4 个叠加来源**，按贡献从大到小排列：

### 1. 每次识图/OCR 都是「全屏原生分辨率截图 + 全屏 Vision OCR」——最大头

代码链路（`tweak/Tweak.xm`）：

- 每个 Lua 调用 `findImage` / `findText` / `ocrText`，最终都走 `ATCaptureScreen()`：
  - `ATScreenPixelSize()` = `UIScreen.bounds × nativeScale`，即**全屏原生像素**。
  - iPhone 8（本机 414×896 逻辑点、@3x）= **1242×2688 ≈ 334 万像素**。
  - 通过 `CARenderServerRenderDisplay` 抓整屏 IOSurface，再逐像素转 RGBA（`w×h×4` 循环，约 13MB 内存搬运）。
- `findText`/`ocrText` 再叠加：全屏图 **PNG 序列化 → 写临时文件 → fork/exec 一个 `ATLOCRWorker` 子进程 → Vision `accurate` 中英双语全屏 OCR → JSON 传回**。
- 即：**一次 OCR = 一次进程 fork + 一次 PNG 编解码 + 一次 Vision 神经网络全屏推理**，这是手机最烫的操作。
- 脚本 `美国完整流程.at` 里 `ocrText()` 被大量循环调用（AMG读IP、AppStore安装、Safari清理、小火箭状态等环节几乎每处都 `for _,b in ipairs(ocrText())`）。

### 2. 密集轮询循环里反复截图

主脚本里大量 `for i=1,N do ... findImage/findText ... msleep(...) end` 轮询：

| 位置 | 轮询规模 |
|---|---|
| `US_准备_AMG监测` | 25 轮 × 800ms，每轮多次 findImage |
| `US_准备_AppStore安装` | 最多 75 轮 × 4 秒，`findText('OPEN')` |
| Safari 清理 / 小火箭状态 | 多轮 OCR 全屏扫 |

每轮都重新全屏截图 + 匹配，长时间跑号时 CPU/GPU 持续满载 → 持续发热。

### 3. Vision OCR 用「精确」模式 + 中英双语

`ocr/main.m:90-94`：

```objc
request.recognitionLevel = VNRequestTextRecognitionLevelAccurate;  // 精确，非 Fast
request.recognitionLanguages = @[@"zh-Hans", @"en-US"];           // 双语
request.usesLanguageCorrection = NO;
request.usesCPUOnly = NO;                                          // 走 GPU/ANE
```

`accurate` + 双语是 Vision 最重配置。Vinted 注册页基本全英文，`zh-Hans` 是额外开销。

### 4. 已有节能机制，但没覆盖「截图降采样」这个关键点

> **重要更正（2026-11-08 16:23 实测核实）**：以下缓存优化（`gEnergyFrame`/`gEnergyOCR`/`gEnergyTemplates`）**只存在于 `ATLite-energy-mode` 分支**，
> 而**当前真机跑的是 `ATLite-US-region` 的 0.3.44**，其 `tweak/Tweak.xm` 里 grep `gEnergyFrame`/`gEnergyOCR`/`gEnergyTemplates`/`withScreen` **全部为空**，即这些缓存**并未实装上线**。
> 因此当前真机的真实状态是「零缓存 + 全屏原生分辨率 + 精确级双语 OCR」，发热比本文第 4 节原描述更严重。详见同日 memory 日志。

`ATLite-energy-mode` 分支里**已经做了**的优化（尚未上线到真机）：

- 模板缓存（`gEnergyTemplates`，LRU 8MB）；
- 帧级截图缓存（`gEnergyFrame`）与 OCR 结果缓存（`gEnergyOCR`）——同一轮内连续调用可复用；
- 事件节流（E25，最小事件间隔 8ms）；
- 抓屏超时门禁（>1.5s 即禁用本次会话）；
- 模板/OCR 计数日志（`energy summary captures=... ocr_requests=...`）。

**但即便 energy-mode 分支，也缺了最关键一招：截图和 OCR 输入始终是全屏原生分辨率，没有降采样。** 这是发热的根。

## 二、优化方案（4 条，按性价比排序）

> 落地可行性受一个前置约束影响：**P-26（本地构建 dylib 真机不加载）尚未解决**。凡是需要重新编译 dylib/worker 的方案（A、B）都依赖先解决 P-26。

### 方案 A：截图降采样（最有效，需重编 dylib）

- 改 `ATCaptureScreen` / `ATRenderIntoNewSurface`：把 1242×2688 缩到 **1/2（621×1344）或 1/3** 分辨率。
- 模板匹配需同步把模板按同比例缩小（或改在匹配时用同分辨率）。
- OCR 输入 PNG 也随之变小，worker 的 Vision 输入更轻。
- **预期效果：CPU/GPU 负载降 50%~75%**。OCR 对小字识别可能略降，需真机核对（注册页文字字号较大，影响可控）。
- **风险/依赖**：需重编 dylib；受 P-26 阻碍。

### 方案 B：OCR 改 Fast + 单语言（次有效，需重编 worker）

- `ocr/main.m`：
  - `recognitionLevel` → `VNRequestTextRecognitionLevelFast`；
  - `recognitionLanguages` → 仅 `@[@"en-US"]`（Vinted 注册页为英文；如需保留中文场景再评估）。
- **预期效果：单次 OCR 耗时与能耗显著下降**（Fast 比 Accurate 快一个量级）。
- **风险/依赖**：需重编 `ATLOCRWorker`；Fast 模式对小字/低对比文字召回率下降，需真机核对各环节识别是否仍达标。

### 方案 C：脚本层减少 OCR/截图调用（不改 dylib，可立即做，风险最低）

- 改 `美国完整流程.at`，把「全屏 `ocrText()` 盲扫」改成「先 `findImage` 定位区域，再按需局部 OCR / 直接坐标点击」。
- 具体切入点：
  - `US_准备_AMG读IP`：当前 `for ipairs(ocrText())` 全屏扫 IP，可改为「先 `findImage` 定位底部状态行区域，只在区域内 OCR」。
  - `AppStore安装` / `Safari清理` / 小火箭状态：把多处 `ocrText()` 全屏扫改为区域化或改为 `findImage` 模板优先（脚本注释本身已写明「识图优先、OCR 兜底」的设计意图，这里进一步收紧 OCR 兜底频率）。
  - 加大轮询 `msleep` 间隔（如 AMG监测 800ms→1000ms、AppStore安装 4s→5s）。
- **预期效果：减少 OCR 调用次数，发热按调用次数线性下降**。
- **风险**：极低，不碰编译；但需保证识别准确率不回退（脚本有「识图优先 OCR 兜底」的设计，收紧 OCR 需逐环节验证）。

### 方案 D：空闲时降频/暂停（不改 dylib）

- 确认跑号间隙没有空转：
  - 脚本 `while true` 主循环里，失败后 `msleep(15000)` 才取下一个账号，成功则立即继续（无 UI 副作用契约）。
  - 账号跑完后 `log('本次运行结束')` 即退出，无后台空转。
- 若仍希望进一步控温，可在「领取账号前 / 换号等待」插入更长 `msleep`（如失败等待 15s→20s），但会降低吞吐，需权衡。
- **预期效果**：对「连续跑号」的峰值发热帮助有限（发热主要在跑号中的密集识图），对「空闲」发热无影响（本就无空转）。

## 三、组合建议（供决策，未实施）

1. **立即做（低风险、高性价比）**：方案 C + D，只改 Lua 脚本，不碰编译。可先把「全屏 OCR 盲扫」逐处收敛为「区域 OCR / 模板优先」，预期发热明显下降，且不影响识别正确性可逐环节验证回退。
2. **彻底解决（需先攻 P-26）**：方案 A + B，重编 dylib + worker。截图降采样 + Fast OCR 是治本手段，预计总负载降 50%+。
3. **推荐路径**：先 C/D 缓解当务之急，同时并行攻 P-26（本地构建真机不加载），解决后再上 A/B 彻底治本。
