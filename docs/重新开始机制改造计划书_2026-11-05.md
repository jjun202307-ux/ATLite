# 重新开始机制改造计划书（2026-11-05）

## 1. 背景：为什么前几轮修复都"没反应"

11-04 晚到 11-05 凌晨的三次运行失败，表面是三个不同报错，实际是**同一个根因**：
脚本每次重启，`phoneFlow('begin')` 在原生层被"保护现场"的设计拒绝，而每一轮
我只修了触发拒绝的那一个条件（权限、断点文件、管理器账号匹配），没有动设计本身。

| 时间 | 日志报错 | 出处 | 设计意图 |
|---|---|---|---|
| 18:02:48 | 本机断点损坏，保留现场，不重新开始 | ATLPhoneFlow.m:99 | 断点文件不可读 → 拒绝一切动作，等人来处理 |
| 18:13:09 | 手机仍有已有注册任务，请先核对，不执行新的准备操作 | ATLPhoneFlow.m:139 | Registration 目录有残留任务 → 拒绝开始新账号 |
| 之前多轮 | 当前步骤已执行3次 / 旧任务不能自动换账号 | ATLPhoneFlow.m:154 / :116 | 防重放、防覆盖 |

这些"拒绝并等待人工"的设计，与 2026-11-05 用户定下的新规则直接冲突：

> **规则：断点续跑功能废除。脚本停止后重启 = 上个未完结账号在工作台标记"失败"，
> 手机直接领取下一个账号。上个账号的手机端现场由系统自动归档，不允许任何环节
> 以"保护现场"为由拒绝开始。**

## 2. 现状链路（begin 一次请求经过的关卡）

```
[Lua 脚本] phoneFlow('begin')
    │
    ▼
[Tweak l_phoneFlow] ──► ATLPhoneFlow(base, "begin")
    │
    ├─ 关卡1  ATLRegOpen：目录非0700/锁被占 → "手机流程状态正在使用或权限不正确"   ← 合理，保留
    │
    ├─ 关卡2  读断点：文件存在但不可读(权限≠0600/内容坏) → "本机断点损坏，保留现场"  ← ★改：旁路归档后续行
    │
    ├─ 关卡3  工作台同步：写 request → 等管理器 reply（20秒）
    │            管理器（已改）：旧账号非终态 → 标"失败" + 回 replace=true + 新账号配置
    │
    ├─ 关卡4  replace=true 且有断点：
    │            旧state=blocked / old_status非终态 / 新旧邮箱相同 → "旧任务不能自动换账号" ← 合理，保留
    │            否则：归档断点 + 归档注册任务 + 写results.txt + 删除 → 开始新账号        ← 已通
    │
    ├─ 关卡5  无断点（新手机/已清理）但 Registration/registration-job.json 残留
    │            → "手机仍有已有注册任务，请先核对"                                   ← ★改：按失败归档后续行
    │
    └─ 关卡6  results.txt 已有该邮箱完成记录 → "不会再次注册"                        ← 合理，保留（防重复注册）
```

## 3. 目标链路（改造后）

```
[Lua 脚本] phoneFlow('begin')
    │
    ├─ 关卡1  锁/目录权限 → 拒绝（保留）
    │
    ├─ 关卡2  断点不可读 → rename 旁路为 archived-corrupt-<uuid>.json（不读内容、不看权限）
    │            请求工作台时 email=''  → 管理器按"来历不明旧账号"发新账号
    │
    ├─ 关卡3  工作台同步（管理器规则不变）
    │
    ├─ 关卡4  replace 归档路径（不变）
    │
    ├─ 关卡5  Registration 残留任务 → 尽力解析：可读则 ATLRegistrationArchiveResult("error")
    │            不可读则 rename 到 Retired/corrupt-<uuid>.json → 继续
    │
    └─ 关卡6  results.txt 查重（保留）→ 创建新断点，state=ready, attempts 清空
```

原则：**每个环节"拒绝并等待人工"改为"归档现场 + 继续"**；归档永远用改名/写新文件，
不删数据；防重放（锁）、防服务端阻止、防重复注册三处保留。

## 6. 风险与回滚

- **风险1：归档时误伤正在运行的另一脚本** — 关卡1的排他锁已排除（同一 PhoneFlow
  目录同时只有一个脚本能拿到锁）。Registration 目录无锁，但单手机单脚本场景下
  残留任务必然属于已停止的旧运行。接受。
- **风险2：CI 构建失败** — 原生改动只用 Foundation/POSIX 已有 API（renameat、
  NSFileManager），无新依赖；CI 绿前不安装。
- **风险3：新版误归档了"其实还活着"的任务** — 手机上残留任务的 state 由
  tweak 启动时的 ATLRegistrationRecover 先行规范化（preparing/submitting 等
  → review），真正运行中的脚本持有 PhoneFlow 锁、走不到关卡5。接受。
- **回滚**：`dpkg -i` 旧版 deb（保留 11-04 的 0.3.36 deb 于电脑）；手机上所有
  归档文件（archived-*.json、Retired/*.json）均保留可查。
