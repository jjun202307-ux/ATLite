### P-01 建议去等 GitHub CI、还说「D2 只有 Xcode 能修」 — 已解决

- **解决**：查会话记录确认构建链路；在 WSL 里查到 ld64-609 二进制自带 `fixup_chains`；

- **教训**：回答前先读上下文和文档；对工具链能力先做 5 分钟实证再下结论。

### P-02 把「41 项门禁全绿」写得像可以装了 — 已认错订正，但包仍装不上
- **现象**：技术正本第九节写「要装机须用户明确点头」，读起来只差点头，实际真机不过。

### P-03 计划书里写「替换官方 OCR worker」 — 已解决（规格更正）
- **现象**：把「本地 worker 真机段错误」的解法写成「从 0.3.44 拿官方 worker 覆盖」。
- **根因**：只看到 worker 坏，没考虑版本一致性。
- **取证**：两个包的 ANE entitlements 完全一致（`H11ANEInDirectPathClient` 等 8 项），
  单独换 worker 会造成 0.3.44 / 0.3.45 混装。
- **解决**：规格改为**只核对 entitlements、不替换**。

### P-04 我自己的诊断脚本把 CodeDirectory 解析错，差点得出「官方签名也全坏」 — 已解决
- **现象**：第一版脚本算出官方 0.3.44 双哈希 97/100 页不匹配。
- **根因**：CodeDirectory 头部是 **9 个 uint32**（`magic, length, version, flags, hashOffset,
  identOffset, nSpecialSlots, nCodeSlots, codeLimit`），我按 8 个读；
  且 `hashOffset` 指向的是 **code slot 0**，special slots 在负索引，我却多加了 `nSpecialSlots` 偏移。
- **解决**：修正解析后，官方与本地两个 dylib 的 slot0(SHA1) / slot4096(SHA256)
  页哈希都是 `MISMATCH=0`，签名自洽。避免了一次错判。

### P-05 把 8080 端口当稳定注入判据 — 已解决（口径订正）
- **现象**：回退后即时探测 8080=200，5 分钟后（16:44）连续 3 次 000。
- **根因**：App 挂起后 HTTP 不监听，是历史已登记的间歇现象；同期 DYLD 注入环境、pid、日志都没变。
- **解决**：判断注入一律以 `v0.3.4x loaded in` + `capture symbols ready` 为准；
  技术正本 10.2、10.4 和另外 3 份文档里的「当前 8080=200」逐处改成「间歇，不作判据」。

### P-06 排障小坑（都已解决）

## 二、打包格式与验收器（旧 38 项「假绿灯」）

### P-07 旧验收器 38 项全绿，真机却不加载 — 已解决（工具层）
- **根因**：一条都没查 D1 双哈希签名、D2 chained fixups、D3 SDK、D4 包元数据、D5 封号标签、压缩后缀↔magic。
- **解决**：`tools/verify_artifact.py` 新增 `loadability_gate()`、`compression_problems()`、
  `sdk_report()`、`control_version()`、`code_directory_slots()` 等，形成 D0–D6 门禁，
  最终 41 项；官方 0.3.44 全过、旧本地坏包被 D4/D2/D1 拦下。
- **注意**：这只是把「静态可查」补齐，**不等于解决真机加载**（见 P-26）。

### P-08 `build_ar()` 产出无后缀成员却塞 XZ，`dpkg` 读不了 — 已解决
- **现象**：`dpkg-deb` 报 `tar: Archive is compressed. Use -J option`。
- **根因**：dpkg 按 ar 成员名后缀判断压缩格式，后缀和实际 magic 必须一致；
  旧代码写 `control.tar/` / `data.tar/`，里面却是 XZ。
- **解决**：对齐官方 `control.tar.gz`(GZIP) + `data.tar.lzma`(LZMA_ALONE)，后缀与内容一致。
- **证据**：WSL 里 A/B 实证，新格式 `dpkg-deb -I/-c` RC=0，旧格式 RC=2。

### P-09 解包器误判压缩格式 — 已解决
- **现象**：纯 tar 被当成压缩、zstd magic 判错、ar 成员边界没校验、畸形 gzip 直接崩 `zlib.error`。
- **解决**：`tools/verify_roothide_layout.py` 新增 `unpack_member()` 作全项目唯一解压入口，
  `compression_kind()` / `is_tar()` 按 magic 精确识别，`parse_ar()` 加边界校验，
  损坏输入统一转 `ValueError`；拒绝不支持的压缩，不再「假绿」。

### P-10 三轮技能复查打回的问题 — 已解决
- **第一轮**：ar 后缀、空包也全绿、报告硬编码假绿、D3/D5 缺失。
- **第二轮（2 Critical + 5 Major）**：
  `sample_blob` / `members` 一行就能绕过包级门禁；`fat_slice_blobs` 与 `macho_slices`
  两套解析器互相矛盾；顶层 `except Exception` 吞掉 NameError/TypeError 真 bug；
  zstd 假绿；D2 退出码与其它门禁不一致；单分片自证。
- **第三轮（2 Minor）**：畸形 gzip 抛 `zlib.error`、失败路径 `ctl` 未关闭。
- **解决**：门禁强制从 deb 重读、复用 `macho_slices`、收窄异常、拒绝未知压缩、
  D0/D1/D2/D4/D5/D6 统一非零退出、补双分片/畸形 fat/0:0 属主/官方 gz+lzma 输入等测试；
  报告由真实门禁结果和真实 SDK 读数生成，不再硬编码 `limitations`。
- **结果**：Critical/Major 清零后才允许 T5；全套 **127 tests OK**；`py_compile` OK。
- **纪律**：每轮打回都停手修完再继续，没带着 Critical 去构建。

### P-11 包元数据与签名不合官方 — 已解决
- **现象**：属主 0:0 或 1000:1000、`./` 前缀、只有单哈希签名、`OFFICIAL_OWNERS` 放得过宽。
- **解决**：`OFFICIAL_OWNERS` 收紧为 `{(501,20)}`；打包器统一属主 501:20、去前缀；
  `ldid -Hsha1 -Hsha256` 双哈希重签，空 entitlements 用裸 `-S`，捕获 `FileNotFoundError`；
  D5 版本从 control 读，不再写死。

### P-12 WSL 打包环境与权限 — 已解决
- **现象**：`/mnt/c` drvfs 权限恒 777，打包器拒收；默认 zst 压缩校验器不认。
- **解决**：在 WSL 原生路径（`/tmp`、`~/`）里操作，重打包用 `dpkg-deb -Zxz -b`。

### P-13 `verify_static.py` 仍 130 PASS / 1 FAIL — 未解决（挂账）
- **内容**：失败规则「ABI 使用 macOS Xcode 工具链」。
- **根因**：11-06 workflow 改三路矩阵后的字面量检查失配，**不是本轮引入**。
- **处理**：按「没让改的不许改」没动规则，如实登记，等用户拍板。

### P-14 第一次 `make -B` 失败（RC=2） — 已解决

### P-15 链接开关没传进子项目 — 已解决
- **现象**：dry-run 看到 10 条链接命令都没带 `-fixup_chains`。
- **解决**：副本 Makefile 里改成 `export ADDITIONAL_LDFLAGS = -Wl,-fixup_chains`，

## 四、真机装机与运行环境

### P-19 装机前基线注入掉了 — 已解决
- **现象**：0.3.44 在机上，但 8080=000、tweak.log 停在 12:55。
- **解决**：重建 `/usr/lib/systemhook-*` 链接 → `killall -9 SpringBoard` → 等 22 秒，
  16:35:29 出现 `v0.3.44 loaded in` + `capture symbols ready`。**先修好基线再装**，否则无法判断新包好坏。

### P-20 注入整体掉了的真实根因（历史经验，本轮沿用） — 已解决
- **根因**：`/usr/lib/systemhook-<随机名>.dylib` 链接丢了，而 launchd 给 SpringBoard 设的
  `DYLD_INSERT_LIBRARIES` 还指向它，dyld 对不存在的 insert library **静默忽略**，
  所以 `killall` / `kickstart` / `ldrestart` 全无效。
- **解决**：`ln -sfn /basebin/systemhook-E2E1AA692F5DE654.dylib /usr/lib/...` + killall。
- **纪律**：以后注入掉了先查 `launchctl procinfo <pid>` 里 DYLD 路径的文件是否存在，别反复 respring。

### P-21 重启 SpringBoard 会重放残留命令、意外跑号 — 已解决
- **前科**：19:40 那次装机，重启重放了 09:06 残留 `command.json`，脚本连做 3 个账号并本地失败。
- **解决**：装 / 退 / 重启前一律先移走 `command.json`、确认 `stop.flag=1`。
  本轮 4 次重启都执行，`status.json` 始终 `running=false`，**未跑号、未误标账号**。
- **附带**：`command.json` 正确路径是 `/var/mobile/Library/ATLite/command.json`，
  格式 `{cmd,script,commandId,stopSnapshot}`，run 的 `stopSnapshot` 必须是 stop.flag 内容的 base64，
  传 null 会立刻 STOP。

### P-22 装完属主变 `mobile:staff` — 已解决（并排除为故障原因）
- **解决**：`chown -R root:wheel` 到 `ATLite.app`、`ATLiteTweak.dylib`、`ATLiteTweak.plist`；
  改完后 0.3.45 仍不加载，**属主被排除**。

### P-23 `uikittools Unable to register ...ATLite.app` — 非故障
- roothide 既有现象，装 0.3.45 和回退 0.3.44 两段都出现，`dpkg` RC=0；记录但不误判。

### P-24 19:40 那次 0.3.45（38 项版）装机也失败 — 已回退

## 五、把踩过的坑固化成流程（以后照这个做）

1. **装机前先做基线**：确认当前版本 `loaded in`、`command.json` 不在、`stop.flag=1`，基线不绿就不装。
2. **A-B-A 对照才下结论**：A 加载 → B 新包 → A' 回退，除「包」外动作完全一致。
3. **静态门禁全绿只是「可以送检」，不是「可以装机」**；真机 `loaded in` 才是放行条。
4. **不重复「打包 → 门禁全绿 → 装机」**：这条路已连着两次（19:40 的 38 项版、本轮 41 项版）失败。
   下一版必须先有真机可加载实证再装。
5. **技能复查每轮打回就停手修**，Critical/Major 清零才允许构建，不浪费构建次数。
6. **注入掉了先查 procinfo 的 DYLD 路径文件是否存在**，别反复 respring；等 20 秒以上再判。
7. **重启 SpringBoard 前先清 `command.json`**，否则会重放跑号。
8. **改动同步四处文档**（技术正本 / BUILD_STATUS / 更新记录 / 应用目录技术说明）+ 项目日志。

## 六、下一步的三个方案（都还没动手，需用户点头）

| 方案 | 做法 | 能解决什么 | 风险 / 代价 |
|---|---|---|---|
| **A 定位根因** | 对 arm64e 分片做定向实验：不补 ABI 位重签、只保留 arm64 分片、逐个对比 chained fixups 指针格式与 imports 表 | 找出到底哪一字节让 dyld / 注入器不接受，为本地构建彻底修好铺路 | 可能要多次装机验证，仍需遵守 A-B-A 与回退纪律 |

| **C 先补封号标签（推荐）** | 只把「封号」UTF-16LE 常量定向打进官方 0.3.44 的 `ATLiteTweak.dylib`，其余字节不动、重新双哈希重签，单独真机验收 | 改动面最小，能先把用户要的封号标签补上，其余功能保持已验证的 0.3.44 | 二进制 patch 必须保证页哈希重签正确；仍需一次真机加载验收，不合格立即回退 |

**当前建议**：C 最快能交付可用结果；A 是彻底修好本地构建的正路。两条不冲突，但都要用户先定。
